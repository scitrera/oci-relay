# Provider startup and receiver import optimization

Host and network labels in this public record are anonymized.

2026-10-04, Sparkrun 0.4.0 `develop-next`, Linux arm64 DGX Spark.
Continuation of the [native-source benchmark](native-2026-10-03.md).
Image distribution/import only; no model application was started.

## Shipped plugin changes

- Independent architecture checks, binary staging, receiver discovery,
  credential writes and direct-route checks run concurrently, capped at eight
  setup workers. Image groups remain serialized and every route must pass
  preflight before any receiver starts pulling. Shared SSH forward allocation
  remains serialized. Failures cancel queued work and join started workers
  before cleanup, preventing late-created resources from escaping cleanup.
- Acquire/verify the controller's release once per architecture per operation.
  Cached target binaries still undergo a full SHA-256 check on every operation
  before execution; hash and version checks share one host command. A changed
  cached binary is replaced, never executed before validation.
- Batch discovery into two commands per host, preserving absent-field handling,
  cgroup ancestor caps, route-specific speed and the Spark effective 100 Gbps
  adjustment. Values travel as positional shell arguments, with fixed field
  framing; targets do not need Python or jq for these probes.
- Log binary, discovery, session, preparation, preflight, transfer/import and
  cleanup timings, including total time through cleanup. Also log per-receiver
  pull/download/extraction times from the existing engine results.

There are no changes to the Go engine, protocol, payload budgets, source
qualification, layer digest checks, or final image identity checks.

## Timing boundaries and workload

Same 25,003,788,800 distinct uncompressed layer bytes and image as the prior
benchmark: `ghcr.io/spark-arena/dgx-vllm-eugr-nightly-b12x:latest`, image ID
`sha256:9633fa21089bc14a230bf7e26943204dcde204761a93957e344dd4f0a99d0b68`.
Source `controller`, receivers `host-b` and `host-c`, data route `dedicated-data-network`, one effective
100 Gbps port. Native source with 512 MiB rings / 16 acquisition slots.
Default Docker download concurrency remains three. Empty isolated Docker
29.2.1 overlay2 stores are reset between cold runs. OS page caches are not
flushed; cached executable installations are verified on every operation.

`scripts/benchmark-image.py provider` now invokes the actual plugin from entry
through cleanup, including binary checks, discovery and route preflight.
The benchmark's host session redirects only receiver imports to the explicitly
isolated test socket; the provider itself has no benchmark-only configuration.
Source-ID and empty-store safety checks precede timing, independent final-ID
checks follow it. This measures image-copy provider execution, not all of
`sparkrun run` (recipe resolution, initial registry pull, model or launch work).

The older `relay` method retains its original narrower boundary: it excludes
binary deployment, discovery, final verification and cleanup, but includes
session setup, readiness and copy/import. Do not subtract a `provider` total
from a `relay` total to claim an optimization.

## Startup comparison

For these measurements the same image was already in both isolated receiver
stores. Every run acquired **zero layer bytes**, so the difference isolates
provider overhead. Sparkrun normally filters whole-image matches before calling
the provider; this is a controlled setup measurement, not a claimed normal
already-present-image latency. Two sequential samples per implementation:

| Provider implementation | Run 1 | Run 2 |
|---|---:|---:|
| Original serial setup | 15.367 s | 15.170 s |
| Parallel setup, original probes/cache checks | 8.982 s | 8.961 s |
| Final parallel setup + batched probes/cache checks | 5.518 s | 5.327 s |

Mean overhead fell **15.269 → 5.423 seconds**, saving **9.846 seconds (64.5%)**.
In the last run, binary checks took 0.972 s, discovery 0.684 s, session setup
0.665 s, native readiness 1.454 s, route preflight 0.361 s, cached pull/result
handling 0.504 s and cleanup 0.687 s. This saving is mostly fixed per operation;
it is especially useful for small missing-layer updates and more hosts.

## Complete cold copy with default Docker settings

The final optimized `provider` run, after restoring default settings and
resetting both test stores, completed in **120.692 seconds**, including all
plugin setup and cleanup. Preparation took 1.532 s and transfer/import 115.367 s.
Both receiver Docker IDs matched the source. This is roughly half the earlier
builtin save/load measurements of 237.084 / 239.362 s; those are the prior
same-image/same-host reference runs, not a fresh paired baseline.

The earlier native result of 120.329 s used the narrower `relay` timer; the
similar numbers do not mean this turn saved no startup time. The controlled
zero-byte A/B above measures the approximately 10-second overhead reduction.
This full cold run does not establish faster payload transfer or extraction.
Downloads finished at 32.542 / 33.389 s; extraction at 114.786 / 114.160 s.
The remaining roughly 81–82 seconds after download is still receiver import.

Source acquisition was 36,809,080,320 bytes, including five bounded replays as
receivers' demand diverged, with five peak acquisitions and 352,649,216 peak
ring bytes. Replays retain full verification and are not extra unique layers.
They varied across this series; unlike the earlier native run, these results
do not claim zero replays. [Structured results](startup-2026-10-04-results.json)
record all ten runs, timing boundaries and isolated daemon variants.

## Receiver CPU profile and controlled scheduling experiment

An additional default-scheduling cold run with debug/profiling enabled only in
the disposable daemons took **116.507 s** using the older `relay` boundary.
Receiver pulls finished in 113.129 s / 110.414 s, after downloads finished in
32.046 s / 32.041 s. CPU profiles were sampled for 55 seconds: `host-b` starting
near transfer startup, `host-c` starting 39 seconds later, covering the import tail.

The tail profile recorded 53.89 CPU-seconds in 55.15 wall-seconds. Its largest
flat entries were syscalls (20.60%), runtime futex (18.95%), CRC64 (14.42%) and
SHA-256 (12.40%). The flate compressor accounted for only 2.88% cumulatively.
These are **CPU sample shares**, not a partition of wall-clock delay. Evidence:
[early profile](startup-2026-10-04-receiver-download-top.txt) and
[tail profile](startup-2026-10-04-receiver-tail-top.txt).

Moby registers layers in parent-chain order; its import path includes
tar-split, SHA-256 and filesystem extraction. The profile supports investigating
receiver work before additional network parallelism or transport compression.
Sources: [download manager](https://github.com/moby/moby/blob/docker-v29.2.1/daemon/internal/distribution/xfer/download.go),
[layer registration](https://github.com/moby/moby/blob/docker-v29.2.1/daemon/internal/layer/layer_store.go).

The next two cold runs changed only `GOMAXPROCS` in the **owned test daemon**
containers. Debug/profiling was off. Relay settings were unchanged:

| Test | `host-b` setting / pull | `host-c` setting / pull | `relay` total |
|---|---:|---:|---:|
| Default, profiled | default / 113.129 s | default / 110.414 s | 116.507 s |
| First scheduling trial | 2 / 86.724 s | 4 / 108.214 s | 111.659 s |
| Second scheduling trial | 1 / 90.072 s | 2 / 91.104 s | 94.737 s |

The two-thread result improved on both hosts, by about 19–26 seconds against
the profiled default run. One thread did not establish an additional benefit.
The second trial is about 19% shorter than that default whole-copy total, but
this is a small exploratory series, with host/cache/profile effects; it is not
a universal optimal setting or a production guarantee.

`GOMAXPROCS` limits simultaneous execution of Go code. It is distinct from
Docker's download concurrency, relay stream slots, container CPU quota and
the total number of OS threads. See [Go runtime documentation](https://pkg.go.dev/runtime#GOMAXPROCS).
Applying it to dockerd affects the daemon as a whole and ordinarily requires
a daemon restart. The plugin **does not set it or restart normal daemons**.
Mixed workload/build/pull behavior needs separate qualification before an
operator chooses it. We did not modify Docker's importer, bypass hashes, or
write receiver layerdb state.

`docker load` is not assumed to solve the remaining import cost: its classic
implementation first untars the complete input to scratch space and still
registers layers. A separate experiment would need to weigh that staging against
the differing read/progress path. [Moby load implementation](https://github.com/moby/moby/blob/docker-v29.2.1/daemon/internal/image/tarexport/load.go).

## Reproduction

Use `scripts/benchmark-image.py provider --source-mode auto --network-gbps 100`
with `--image`, two `--host` / `--transfer-host` pairs, `--binary`, `--output`
and an owned `--receiver-docker-host unix:///tmp/oci-relay-benchmark.*/docker.sock`.
The script rejects normal receiver sockets and nonempty stores unless `--warm`
is explicit. `--warm` can isolate startup overhead after a cold copy. Normal
Docker daemons and unrelated images must not be pruned for a benchmark.

The tested Go binary remains
`b8359341ab1431fa71b98f67511246904d57bb3c226714d3e66eb6f8ccb98f44` (arm64).

All 78 plugin tests pass, including real source/transport lifecycle checks,
concurrent setup/failure barriers, batched cgroup caps and a tampered cached
binary that must never execute. The CI-style dependency-isolated run passes
60 tests and skips 18 requiring Sparkrun/Docker. Python lint and generated
version/workflow checks pass. The snapshot is vendored into `develop-next`;
its hashes verify and all 59 affected Sparkrun integration tests pass.

Fresh 32 MiB `host-a` → `host-d` copies also pass direct HTTP/2, SSH forwarding and
SSH stdio with auto selecting native, exact final IDs, zero replays, and 2 MiB
peak rings. These take 9.274 / 9.557 / 9.163 seconds through provider cleanup;
the source is remote here, unlike the local-source setup A/B above.

All owned helper containers, test daemons/volumes, operation directories and
fixture images were removed. Final audits on the controller and all four
cluster hosts report zero relay processes, owned operation/test directories
or fixture tags. Verified binary caches and private benchmark evidence remain.
No user-daemon settings, models, commits, pushes or published releases changed.
