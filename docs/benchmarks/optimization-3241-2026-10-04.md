# Daemon-independent optimizations: 3 → 2 → 4 → 1

Host and network labels in this public record are anonymized.

2026-10-04, Sparkrun 0.4.0 `develop-next`, Linux arm64 DGX Spark.
[Structured measurements](optimization-3241-2026-10-04-results.json).
Continues the [startup/import investigation](startup-2026-10-04.md).

The requested order was followed: source replay reduction, cached-layer reuse,
relay-only tuning, then full native streaming load. Normal Docker daemon
configuration was unchanged. No model application was started.

The strongest result is cross-representation cache reuse: a 32 MiB compressed
base plus 1 MiB child required **34,606,080 bytes** with normal native pull but
only **1,050,112 bytes** with selective load, preserving the exact image ID.
The cold-copy experiments do not justify changing defaults. Full streaming
load was slower, and the slot/CPU changes need repeated evidence before an
automatic tuning policy can prefer them.

## Workload and measurement boundaries

The large workload is the same recipe image used in previous measurements:
`ghcr.io/spark-arena/dgx-vllm-eugr-nightly-b12x:latest`, Docker ID
`sha256:9633fa21089bc14a230bf7e26943204dcde204761a93957e344dd4f0a99d0b68`.
It contains 25,003,788,800 distinct uncompressed layer bytes: 30 layer positions,
29 unique blobs. Controller `controller` serves `host-b` and `host-c` over `dedicated-data-network`,
using one effective 100 Gbps port. No striping, RDMA or transport compression.

Each cold run starts with empty **owned isolated** Docker 29.2.1 overlay2
stores. The normal host daemons remain unchanged. OS page caches are not
flushed. Default relay limits are a 512 MiB ring budget and 16 acquisition
slots per process; default Docker download concurrency remains three.
Timers cover the actual plugin from entry through cleanup. Empty-store safety
checks and independent final image-ID checks occur outside that timer.
This is image distribution, not all recipe/model startup work.

## 3. Retain the initial source window briefly for other receivers

Added opt-in `source_join_milliseconds` (0–2000, default 0). Acquisition starts
immediately. Before evicting its initial ring prefix, it can wait for the
expected receiver count, bounded from acquisition creation. Cached or absent
receivers cannot hold it indefinitely. This uses the existing memory budget;
there is no extra layer spool. Cancellation, byte limits and full SHA-256
verification are unchanged. New metrics record join waits and summed wait
seconds; sums across streams are not wall-clock delay.

| Native pull run | Total | Source bytes acquired | Replays | Peak acquisitions |
|---|---:|---:|---:|---:|
| 250 ms, first deployment | 126.151 s | 25,016,199,680 | 7 | 3 |
| 0 ms control, cached executable | 120.248 s | 42,945,591,296 | 6 | 5 |
| 250 ms repeat, cached executable | 122.502 s | 25,003,805,184 | 3 | 3 |

The repeat reconstructed only 16,384 duplicate bytes, versus about 17.94 GB
in the control. Replay counts alone are misleading because a replay may be a
small layer. Both 250 ms runs greatly reduced source bytes; they did **not**
reduce complete operation time. The first includes about 2.3 seconds more
binary deployment time. Join waits summed to 0.108 / 0.166 seconds. The default
remains zero; the setting is available for workloads where source I/O matters.

## 2. Reuse a cached parent chain across representations

Added opt-in `receiver_import: load-cached`. The receiver inspects at most 128
listed images through public Docker APIs, matches complete DiffID parent
prefixes, and pins the best base with an owned temporary tag. It streams the
original config and only missing raw layers into a legacy Docker load archive.
Matching config bytes preserve the final image ID.

The same fresh 32 MiB random base was first imported in compressed form into
both isolated stores. A child adds 1 MiB. The native source then supplies exact
uncompressed descriptors for that child:

| Importer / host | Transferred layer bytes | Receiver import | Complete provider |
|---|---:|---:|---:|
| Normal registry pull / `host-b` | 34,606,080 | 0.283 s | 3.996 s |
| Selective load / `host-c` | 1,050,112 | 0.074 s | 3.763 s |

Selective load reused one cached layer and transferred **97.0% fewer bytes**.
Its outer archive was 1,054,720 bytes, safely below the explicit 8 MiB cap
(which could not fit the complete child image). Different receiver hosts and
one sequential comparison limit timing conclusions; the byte avoidance and
matching final IDs directly establish the cache-reuse benefit.

Normal pull's cache lookup on the tested classic store uses the incoming blob
representation's digest. A previously compressed layer can therefore be
redownloaded when presented uncompressed. Selective load uses the public
image DiffIDs and Docker's existing parent-chain cache.
See [Moby pull implementation](https://github.com/moby/moby/blob/docker-v29.2.1/daemon/internal/distribution/pull_v2.go)
and [load implementation](https://github.com/moby/moby/blob/docker-v29.2.1/daemon/internal/image/tarexport/load.go).

This remains opt-in and version-qualified to Linux overlay2 Docker 29.1.3 /
29.2.1 with exact uncompressed OCI descriptors. Unsupported stores/input or
no usable prefix select normal pull before transferring data. Older images
outside the bounded inventory can be missed. Import or hash failures never
trigger fallback. Zero-length cached archive entries do not claim OCI blob
hashes: Docker must find the exact chain; tests verify a missing chain fails
its DiffID check and cannot create the destination image. All transferred
layers retain full relay SHA-256 verification and final-byte withholding.

Both load modes require an explicit `max_import_bytes` covering the complete
outer tar, including headers, padding and terminator. The relay does not spool
it. Docker stages the archive with its normal buffered I/O before registration.
The budget does not bound extracted Docker storage or RSS. Large entries use
GNU tar headers; the 25 GB test includes a layer exceeding the USTAR size limit.

## 4. Tune relay slots and CPU use only

Added plugin `relay_gomaxprocs` (0–64, default 0/inherit). It is passed only to
relay processes, including the owned source helper, never to dockerd. Existing
`source_streams` remains the acquisition ceiling; neither control changes
Docker's download concurrency. Slots are not independent pieces within a blob.

| Cold native pull | Total | Last source verification | Last receiver downloads | Peak acquisitions |
|---|---:|---:|---:|---:|
| Control, 16 slots / runtime default | 120.248 s | 34.289 s | 17.325 / 33.387 s | 5 |
| Four slots / runtime default | 117.869 s | 32.020 s | 31.308 / 31.339 s | 4 |
| 16 slots / relay GOMAXPROCS=4 | 119.924 s | 29.218 s | 28.511 / 28.510 s | 3 |

The four-slot run was 2.38 seconds shorter, but this single sample does not
establish a generally better default. It reached the entire 512 MiB ring
budget, acquired 25,527,883,264 bytes and had 21 mostly small replays. Lower
slot counts also increase the per-acquisition share of a fixed buffer budget.
The CPU-limited relay shortened downloads but left overall time nearly equal
to the control. Receiver registration still dominates. Defaults remain
unchanged; the controls make repeated workload-specific tuning possible.

## 1. Full native streaming load, tested last

`receiver_import: load` uses the same quiet ImageLoad API without a cache
probe, streaming all unique raw layers. This cold run had an explicit 32 GiB
archive cap and otherwise default relay settings:

- Total provider time: **135.060 seconds**, versus 120.248 for registry pull.
- Receiver import: 129.281 / 126.031 seconds; both final IDs match the source.
- Source verified all 25,003,788,800 bytes in 43.997 seconds, with zero replays
  and one peak acquisition. The archive was 25,003,849,216 bytes.

That is about 12.3% slower than the control. A sequential load archive limits
source demand to one layer at a time and Docker still stages and registers
the input. This result does not support using full load for cold distribution.
Its download/extraction phase fields are zero because quiet load does not
expose those events; they do not mean those operations took zero time.

The earlier builtin SSH save/load measurements were 237.084 / 239.362 seconds.
Current native pull remains roughly twice as fast for this image, but those
are historical same-workload references, not a fresh paired baseline here.
