# Read-only classic-store source: performance and integrity

Host and network labels in this public record are anonymized.

2026-10-03, Sparkrun 0.4.0 `develop-next`, Linux arm64 DGX Spark.
This follows the [original DeepSeek image benchmark](deepseek-2026-10-03.md).
It measures image distribution/import only; no model application was started.

## Implementation

The opt-in `docker-classic` adapter reads Docker's existing tar-split metadata
and layer files through read-only mounts. It uses upstream `vbatts/tar-split`
v0.12.3 to reconstruct the **original tar byte stream**, including headers,
whiteouts, file order and padding. It does not regenerate a tar from a directory
walk, ask Docker to push/compress, or wait for `docker save` to build an archive.
[Moby uses the same reconstruction library](https://github.com/moby/moby/blob/docker-v29.2.1/daemon/internal/layer/layer_store.go).

Preparation parses metadata to calculate exact descriptor sizes, without
reading file payloads. A plugin-owned helper container pins the source image
for the operation; its entrypoint is the verified static relay. The image's
normal application is not started. Docker metadata and layer trees are mounted
read-only, with no Docker socket exposed to the helper. The operation directory
is the only writable host bind. All capabilities are dropped except DAC_OVERRIDE
and CHOWN, needed for reading root-owned files and returning the private socket
to the coordinating user's ownership. The root filesystem is read-only and
no-new-privileges is enabled. Only rootful Docker 29.1.3/29.2.1 classic overlay2
is qualified; this is an explicit exception to the public-API-only design.

Integrity boundaries:

- Exact config bytes must hash to the immutable source Docker image ID.
- Layerdb DiffIDs and parent chain IDs must agree with that config.
- Uncompressed descriptors must equal their corresponding config DiffIDs.
- Paths are confined using `os.Root`; payload opens cannot escape the layer.
- Tar-split checks file CRCs. The source and receiver additionally check the
  complete tar SHA-256 and exact byte count, withholding the final byte until
  verification succeeds. CRC is not the cryptographic integrity boundary.
- Docker verifies import and the relay checks the final Docker ID/platform
  before assigning the requested destination tag.

Tests include exact reconstruction with links and extra padding, concurrent
reads, preparation without accessible payloads, incorrect parents/config/
DiffIDs, escaping symlinks, cancellation, changed payloads, and changed tar
headers with untouched file contents. Corruption cannot complete the blob.

## Controlled workload

Same source image and hosts as the original benchmark:

- Source `controller`: Docker 29.1.3; destinations `host-b` and `host-c`: isolated empty
  Docker 29.2.1 overlay2 stores, reset between cold runs.
- Image `ghcr.io/spark-arena/dgx-vllm-eugr-nightly-b12x:latest`.
- Docker/config ID `sha256:9633fa21089bc14a230bf7e26943204dcde204761a93957e344dd4f0a99d0b68`.
- Uncompressed manifest `sha256:6a2afe5c2b37ff21ebcfbb9523e59d1907837ef15248e51589628dec4f0bae3b`.
  This exactly matches Docker's previously measured uncompressed export
  manifest. It differs from the registry's compressed manifest.
- 30 layer descriptors, 29 distinct layer blobs; a repeated 1,024-byte empty
  layer accounts for the difference. Each receiver required 25,003,788,800 bytes.
- Source decoded 225,440,984 bytes of tar-split metadata during preparation.
  It did not stage any layer payload. Ordinary buffered filesystem reads apply;
  the ring budget does not include metadata decoding or filesystem page cache.
- Data route `dedicated-data-network`, effective 100 Gbps single port. Relay budgets:
  512 MiB rings and 16 acquisition slots per process. No bonding, RDMA or
  multi-NIC striping. OS page caches were not flushed.
- Deployment/probes precede timing, matching cached binaries. Session setup,
  source helper startup, preparation, transfer and Docker import are included.
  Verification/cleanup follow the timer. Original baseline methods are unchanged.

## Results

| Method | Source readiness | Transfer + import | Total |
|---|---:|---:|---:|
| Builtin parallel SSH save/load, original run | included | included | 237.084 s |
| Builtin parallel SSH save/load, repeat | included | included | 239.362 s |
| Indexed `docker-save` relay, original run | 127.703 s | 115.401 s | 247.096 s |
| `docker-classic`, default 3 Docker downloads | 1.517 s | 117.401 s | 120.329 s |
| `docker-classic`, 8 Docker downloads (isolated daemons only) | 1.487 s | 119.200 s | 122.140 s |

The default-daemon run is about **49% less elapsed time**, or **1.97–1.99× faster**
than the two builtin runs. Source metadata scanning itself took 1.253 seconds;
the readiness measurement also includes Docker probes and helper startup.

All required source layer bytes were reconstructed and SHA-256-verified by
45.308 seconds after cache creation, with **zero replays**, three peak active
acquisitions and 252,772,352 peak ring bytes. Both receivers verified all 29
unique blobs, had zero replays, and finished downloads around 44.96 seconds
after their pull started. Final extraction/registration finished at 116.90 and
111.86 seconds. The approximately 67–72-second tail is receiver import work,
not unfinished network transfer. A sampled receiver daemon used about one CPU
core during that tail; this is a sample, not a full CPU/storage profile.

The eight-download run raised measured peak source acquisitions to eight and
finished source verification by 32.794 seconds, with zero replays and
298,123,264 peak ring bytes. Receiver downloads finished around 32.44–32.47
seconds, but extraction finished at 114.35 and 118.78 seconds. **Total time did
not improve**; the 1.8-second difference is not enough evidence of a regression
either. Keep normal daemon settings unchanged. Increasing transfer parallelism
is not the immediate end-to-end bottleneck for this image.

Both cold runs preserved the exact Docker IDs and uncompressed manifest on
both receivers. [Structured results](native-2026-10-03-results.json) retain
phase times, actual concurrency, byte counts and cleanup outcomes. This is two
native cold runs with different Docker limits, not a statistically controlled
series. A fresh third builtin run was not repeated after this change; the two
prior same-image/same-host builtin runs are the comparison.

## Cached-layer reuse

A child image with a fresh incompressible 32 MiB layer was copied to those same
stores after the base image completed. It took 3.944 seconds overall, including
1.580 seconds readiness and 1.001 seconds copy/import. Source acquisition was
only **33,555,968 bytes / one verified layer**, with no replays. Both destination
IDs matched the child config. This demonstrates reuse after a prior transfer
of the same uncompressed representation.

This does not establish the same reuse when switching from registry-compressed
layers to uncompressed descriptors for the first time. Classic Docker's digest
mapping can require those layers to be downloaded again. The whole-image
already-present case remains skipped by Sparkrun before provider invocation.

## Reproduction and limits

With explicitly owned, empty test Docker daemons as described in the original
benchmark, use `scripts/benchmark-image.py relay --source-mode docker-classic`
with the same image, two hosts, two data addresses, binary, isolated socket and
`--network-gbps 100`. The script refuses normal receiver Docker sockets.
`--warm` explicitly permits cached images in an isolated store for incremental
checks. `scripts/qualify-cluster.py --source-mode docker-classic` covers the
plugin's direct, forwarded and stdio routes using fresh disposable images.

These are observed results for this image, not a universal speed guarantee.
The private-store mode is explicit (`allow_native_store: true`), while the
public Engine API modes remain available. Relay frames are still bounded
buffers, not independently scheduled pieces. Each blob has one HTTP stream.
Docker's download limit governs missing-layer demand; raising the relay's
ceiling alone does not raise that limit. The plugin does not reconfigure or
restart normal Docker daemons.

## Next optimization boundary

The largest eliminated cost is source preparation: about 128 seconds became
1.5 seconds. Full-blob parallelism already exceeds the useful overlap for this
workload once downloads finish well before import. Before implementing piece
striping, a second NIC, streaming compression or RDMA, profile receiver layer
extraction and tar-split/metadata registration separately. The eight-download
comparison demonstrates that shortening this transfer phase by 12.5 seconds
alone does not shorten the full operation. Changing the image store or runtime
(e.g. a lazy snapshotter) would be a separate compatibility project; this plugin
does not alter normal daemon storage or write layerdb metadata.

All benchmark helpers, isolated daemons/volumes and disposable tags were removed.
Post-run audits found no relay processes or owned operation directories on the
controller or any of the four cluster hosts. Verified executable caches remain.
