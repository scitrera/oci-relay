# DeepSeek V4 Flash recipe validation and image-copy benchmark

Host and network labels in this public record are anonymized.

**Update:** the subsequent [read-only classic-store source benchmark](native-2026-10-03.md)
reduced cold image distribution to 120–122 seconds, with verified layer hashes.
The slower public-API paths measured below remain available.

Test date: 2026-10-03. Sparkrun 0.4.0 `develop-next`, Linux arm64 DGX Spark.
The installed `sparkrun` executable was 0.3.10; all tests used the checkout's
public `sparkrun.application.initialize` / `run_cli` entry points instead.

## Large-image failures found and fixed

The first large transfer exposed two coupled source-adapter problems:

1. A verified layer waited for the entire Docker push round before completing
   its acquisition. This withheld its final bytes while unrelated large layers
   compressed, encouraging receiver retries.
2. A consumer-copy failure returned HTTP 500 while retaining the staged upload
   and its reservation. A new Docker upload could wait behind that reservation.

Acquisitions now complete individually after their exact blob is verified and
copied. A failed consumer receives its own error, while its verified upload
releases its reservation and other demands continue. Regression tests exercise
both successful and failed consumers with an unrelated unfinished demand and a
one-upload staging budget. The Docker integration tests and race checks pass.

Cancellation also exposed remote process ownership: stopping the controller's
SSH process could leave a receiver running. Sparkrun streaming processes now
use its existing session guard while preserving binary stdin. A real SSH test
verified the bytes and confirmed that cancelling the handle reaped the remote
child. Direct HTTP/2, SSH forwarding, and SSH stdio subsequently passed fresh
32 MiB transfers between `host-a` and `host-d` with zero replays and cleanup.

Corrected arm64 binary SHA-256:
`3a20046a8dd1d4a1614a8ff502ee5dca4ff73404a341f1a34f561251ac5df199`.
Static amd64 build:
`68a616da3f9dfb8a9106eeea2fd388e779975efeb10aa2f50c902bd2a2113b8b`.

## Recipe run

The corrected relay successfully imported the image on both nodes, verified
their Docker IDs, and continued into container launch and the recipe's hooks.
The relay log interval, including setup and Docker import, was 764.625 seconds.
It acquired 7,309,668,913 bytes with zero replays and 220,266,496 peak managed
source-buffer bytes. This was an update over existing image layers; it is not
the empty-store comparison below. The supplied manifest bypassed the full
metadata-preparation read.

The containers launched and recipe hooks ran. Logs showed main-model loading
in 39.739 seconds and draft-model loading in about 10 seconds, followed by B12x
kernel tuning. At the user's request, further testing was narrowed to image
distribution. The owned deployment was stopped on both nodes before benchmark
runs; serving health and inference were not validated. Future image-copy tests
do not start the model.

Source-acquisition progress, measured from relay start:

| Elapsed | Cumulative source bytes |
|---:|---:|
| 60 s | 811,101,835 |
| 380 s | 2,411,982,475 |
| 385 s | 3,891,870,468 |
| 520 s | 6,996,251,996 |
| 535 s | 7,309,668,913 (all requested bytes) |
| 765 s | Both Docker imports complete |

The full 8 GiB upload reservation with an 8 GiB spool budget admitted only one
unidentified upload at a time. Large gzip preparations and staging delayed
layer availability; about 230 seconds then remained after final source-byte
acquisition. That tail includes downstream transfer and Docker import, not a
measurement of import CPU alone. Neither phase approached the NIC's capacity.

Docker's classic push implementation compresses uncompressed layers; it has no
supported per-push disable-compression option. The client SDK cannot change this
daemon behavior. [Docker 29.2.1 push implementation](https://github.com/moby/moby/blob/docker-v29.2.1/daemon/internal/distribution/push_v2.go).

## Controlled comparison method

`scripts/benchmark-image.py` compares the actual Sparkrun
`run_pipeline_to_remotes_parallel` Docker save/SSH/load path with the relay CLI.
Both use the same source image, receivers and data network. Relay limits come
from the plugin's normal route probes and adaptive policy.

Each receiver has a disposable Docker 29.2.1 daemon with its own empty overlay2
store, run using `docker:29.2.1-dind`. The fixture uses an operation-owned Unix
socket, a separate Docker volume, host networking for the receiver's loopback
registry, and disabled bridge/firewall/IP-forward configuration. It does not
mount or change the normal host Docker store. The fixture is recreated between
methods. No operating-system page caches are flushed.

Timing includes import; final image identity verification is mandatory. The
extra `docker image inspect` checks occur immediately after the copy timer;
relay completion itself already requires the expected Docker ID on each peer.
Binary installation, fixture creation, registry fetch and model startup are
outside the copy benchmark. Fresh-source export cost is included when comparing
the uncompressed relay with the built-in path. The exported representation has
30 uncompressed layers totaling 25,003,789,824 bytes and manifest
`sha256:6a2afe5c2b37ff21ebcfbb9523e59d1907837ef15248e51589628dec4f0bae3b`.
Its config/Docker ID is unchanged. It does not preserve the registry's compressed
manifest digest. A pinned export by image ID may carry different index
annotations from a tagged export; its platform manifest remains identical.

Both methods ran after the model deployment was stopped. Results are small
samples on these machines, without controlled OS page-cache state; they are
not statistical throughput characterizations.

## Measurements

[Machine-readable observations](deepseek-2026-10-03-results.json) contain the
non-secret timing, limits, identity and relay metrics from these runs.

| Method | Preparation | Copy/import | Total for both receivers |
|---|---:|---:|---:|
| Sparkrun built-in SSH save/load, run 1 | included | included | 237.084 s |
| Sparkrun built-in SSH save/load, run 2 | included | included | 239.362 s |
| Export/extract OCI layout, original relay cache | 104.535 s external export | 119.113 s relay operation | 223.648 s |
| Integrated indexed `docker-save` source | 127.703 s | 115.401 s | 247.096 s |

The layout experiment was 5.7% faster than the first built-in run with full
preparation included. Reusing an already prepared layout reduces that case to
119 seconds, but comparing that alone with a fresh Docker save is unfair.
This run acquired 43,451,327,488 source bytes and recorded 10 replays: receivers
joining after ring-prefix eviction caused disk rereads.

The integrated archive source took 247.096 seconds, **3.2–4.2% slower** than the
built-in runs. Its 25,003,902,464-byte archive stayed under the explicit 32 GiB
cap; first export bytes arrived at 103.233 seconds. The source acquired
42,052,212,736 bytes with nine replays and 348,585,984 peak managed buffer bytes.
Both receivers imported the expected image ID, with zero receiver replays and
successful cleanup. The approximately four seconds outside preparation and
copy are operation credential/directory setup. This result disproves a reliable
fresh-source speedup for the current public-API path; the earlier 5.7% result
must not be presented as an established advantage.

A separate `docker save` profile (stdout consumed without storing an external
archive) took 111.921 seconds before the first 512 bytes and 137.420 seconds
overall. Removing gzip therefore does not make classic Docker stream immediately.
Docker's own export preparation remains material and varies between runs.

The new `docker-save` source stages a single indexed archive without extracting
a second copy. It has explicit full-image disk admission, pins the inspected
config ID before export, and reports preparation/first-byte timing. Independent
file-backed replays can now overlap, within the same aggregate slot and ring
budget; expensive push acquisitions still coalesce as before. Live-buffer
accounting no longer scans and locks every entry on each write. The Moby client
was also updated from v0.1.0 (November 2025) to v0.6.1 (October 2026), with API
negotiation and real Docker 29.1/29.2 checks.

## Network direction

Both active Spark data ports expose Ethernet/RoCE, with addresses on
`alternate-data-network` and `dedicated-data-network`. These tests use only the latter route.
They do not measure RDMA or aggregate both links. Multiple TCP connections
must be routed over distinct interfaces to combine paths; adding connections
on the same route is insufficient. Whole-blob path assignment can precede
verified piece/range striping. RDMA is a later optional data path with TCP
fallback, after preparation and import costs are addressed.

## Reproduction and cleanup

Use Sparkrun `develop-next` on `PYTHONPATH` and the same local image ID. Create
explicitly isolated, empty Docker 29.2.1/overlay2 test daemons on the receiver
hosts with operation-owned sockets under `/tmp/oci-relay-benchmark.*`. Recreate
their stores between methods. The script rejects nonempty stores and ordinary
Docker socket paths; do not remove images from the hosts' normal stores.

```sh
PYTHONPATH=plugin/src:../oss-sparkrun/src python scripts/benchmark-image.py builtin \
  --image ghcr.io/spark-arena/dgx-vllm-eugr-nightly-b12x:latest \
  --host host-b --host host-c \
  --transfer-host host-b-data --transfer-host host-c-data \
  --receiver-docker-host unix:///tmp/oci-relay-benchmark.EXAMPLE/docker.sock \
  --binary bin/oci-relay --output builtin.json
# After recreating empty receiver stores, use the same arguments with:
#   relay --source-mode docker-save --max-spool-bytes 34359738368 --network-gbps 100
# and a different output path.
```

The test deployment was stopped. All owned nested Docker daemons, their data
volumes and fixture images, the 25 GB prepared layout, temporary configuration
copies and small archive probe image were removed. A final audit of the
controller and all four cluster hosts found zero relay processes, operation
directories, archive staging directories or temporary relay/test tags.
Verified executable caches and the successfully synchronized normal image tags
remain. Existing model caches and unrelated Docker data were not pruned.
